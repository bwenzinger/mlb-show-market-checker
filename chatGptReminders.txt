Project brain: mlb-show-market-checker

How to use this file
- Treat this file as the durable "brain" of the application, not as a changelog.
- Before making changes, read this file to understand the app's current product behavior, data flow, architecture, and non-obvious decisions.
- When behavior changes, update the relevant canonical section below instead of only appending a dated entry.
- Add dated notes only for temporary context, migration warnings, known one-time issues, or facts that are useful historically.
- Keep this file focused on complete logic: what exists, why it exists, how it works, and what future changes must preserve.
- UI/UX changes should consider the actual page layout and user workflow. Place controls where users naturally need them and make smart, reasonable behavior decisions from the user's perspective.

Purpose
- React frontend plus Node/SQLite backend for exploring the MLB The Show 26 market.
- Main use case: scan market listings, filter/search/sort opportunities, inspect a selected item, and compare live prices against stored completed-order history.
- The app is designed to run locally during development and as a single-machine public/home server behind a systemd service.

Stack and commands
- Frontend: React 19, TypeScript, Vite, Material UI.
- Backend: Node 25+, Express 5, Node's built-in SQLite API (`node:sqlite`), TypeScript via `tsx`.
- Useful commands:
  - `npm run dev`: starts backend and Vite dev server.
  - `npm run market-server`: starts backend only.
  - `npm run collect:once`: runs one collection pass.
  - `npm run typecheck`: TypeScript check.
  - `npm run build`: TypeScript check plus Vite production build.
- Build warning: Vite currently warns that the main JS bundle is larger than 500 kB after minification. This is known.

Critical data safety rule
- `market.sqlite` is live local market-history data and must absolutely never be deleted, reset, overwritten, migrated destructively, or directly modified by AI agents in any way.
- AI agents may read code that references `market.sqlite`, but must not run commands or make code changes whose purpose is to alter, clear, compact, recreate, or remove that database file.

Top-level architecture
- `src/App.tsx` coordinates the list workflow: read URL params, fetch listing data when needed, apply local transforms, choose the selected UUID, and render `SearchPanel` plus `MarketDetail`.
- `src/components/market/SearchPanel.tsx` owns the sidebar UI: search/type/rarity/sort controls, post-query filter drawer, clear-all control, and the virtualized listing list.
- `src/components/market/Detail/MarketDetail.tsx` owns selected-item data loading and detail-state orchestration.
- `src/components/market/Detail/MarketDetailView.tsx` renders the item detail surface.
- `src/components/market/common/` contains shared UI helpers:
  - `DebounceTextField`
  - `ListLoadingState`
  - `MetricCard`
  - `QuickSellBadge`
  - `ProfitMetric`
  - `SectionHeading`
  - `ChartCard`
  - `useQueryParams`
- `src/marketUtils.ts` is the main frontend domain utility file: filter/sort options, normalization, price math, quick-sell fallback, search matching, parsing/formatting, listing fetching, and local list sorting.
- `src/showApi.ts` is the frontend API client for live MLB The Show API proxy calls and local history endpoints.
- `src/server/marketServer.ts` is the backend service: static frontend host, API proxy, SQLite persistence, market collector, and cached average endpoints.
- `src/orderStats.ts` contains robust average logic shared by backend average computation.

URL state and query params
- URL params are the source of truth for list controls and selected item state.
- `useQueryParams` in `src/components/market/common/useQueryParams.ts` uses `useSyncExternalStore`, listens for `popstate`, patches `history.pushState` and `history.replaceState`, and returns stable param references when the shallow key/value shape does not change.
- Typed URL params live in `src/types.ts` as `FilterUrlParams`.
- Current important params:
  - `query`: search text.
  - `itemType`: item type (`mlb_card`, `stadium`, `equipment`, `sponsorship`, `unlockable`).
  - `rarity`: rarity filter.
  - `uuid`: selected listing/item.
  - `sort`: active sort key.
  - `sortDirection`: `asc` or `desc`.
  - `starredOnly`: `1` means show only locally starred listings.
  - `minSpreadForPercent`: minimum spread used only for spread percentage sorting.
  - `profitHrActiveFlipSlots`: optional user override for the Profit/hr active flip slot assumption.
  - `profitHrStubBudget`: optional user override for the Profit/hr working bankroll assumption.
  - `series`: post-query series filter.
  - `minBuyNow`, `maxBuyNow`, `minSellNow`, `maxSellNow`: post-query price filters.

List data flow
- On first load, even with an empty URL, `App.tsx` must fetch listing data. Do not regress this; the previous failure mode was an empty initial list because "previous fetch" and current params were all undefined.
- `App.tsx` decides whether to fetch new list data by comparing `itemType`, `query`, `rarity`, and `series` against the previous fetch key.
- Do not add frontend market-data caching for now. Frontend requests should fetch fresh data when the app workflow asks for data, because flipping-card numbers move rapidly and a 5-minute frontend cache can make the displayed opportunity data pointless. This may change in the future, but frontend caching has already been intentionally removed once.
- `itemType` and `rarity` reduce API work:
  - If `itemType` is selected, only that type is fetched.
  - If `itemType` is empty, all market item types are fetched.
  - `rarity` is passed to the listing API calls.
- Search text currently participates in the fetch key, then matching is applied locally after fetched listing pages are loaded.
- Post-query filters (`series`, min/max buy/sell, and spread minimum) should reuse the current fetched listing array for normal filtering work.
- `starredOnly` is a local post-query filter using the user's locally starred UUID list; changing it or starring/unstarring an item should not refetch listings.
- Series is still applied locally, but player-card series views need one extra data source: when a player/all-type series filter is selected, or when the search text clearly names a series, `fetchListingsByTypeAndRarity` supplements market listings with matching `items.json` catalog cards. This is required because `/listings.json` only contains market/sellable listings, while complete series checklists can include non-sellable cards.
- `App.tsx` stores the fetched/enriched list in `allListings`, applies post-query filters and sorting, then sets `filteredListings` for `SearchPanel`.

Search behavior
- Market search should match more than player/listing names.
- `listingMatchesNormalizedSearch` in `src/marketUtils.ts` currently searches:
  - listing name
  - item name
  - item series
  - item type label
  - item type
- Search text is normalized by removing diacritics, lowercasing, and replacing non-alphanumeric characters with spaces.
- Compact matching supports no-space variants.
- Token fallback supports phrases like `spring breakout cards` matching cards whose series is `Spring Breakout` and type label is `MLB Card`.
- This exists because series searches such as "Spring Breakout cards" should not depend on player names containing the words "Spring Breakout".
- If search text contains a known series phrase, player-card results are supplemented from `items.json` so complete set/checklist searches include non-sellable catalog cards too.

Type, rarity, and series filtering
- Main type options:
  - All
  - Players (`mlb_card`)
  - Stadiums (`stadium`)
  - Equipment (`equipment`)
  - Sponsorships (`sponsorship`)
  - Unlockables (`unlockable`)
- Rarity options:
  - All
  - diamond
  - gold
  - silver
  - bronze
  - common
- Series is a post-query filter shown in the filter drawer.
- Series options are derived dynamically from the current fetched listing set. Do not hard-code the series list; new API values should appear automatically.
- Player-card series lists can include catalog-only cards from `/api/show/items.json`. These rows have no market buy-now/sell-now price and should sort to the bottom of price sorts.
- Example series values seen locally: `2nd Half Heroes`, `All-Star`, `Awards`, `Breakout`, `Contributor`, `Default`, `Egg Hunt`, `Last Ride`, `Live`, `New Threads`, `Postseason`, `Spotlight`, `Spring Breakout`, `St. Patrick's Day`, `Standout`, `Topps Now`, `Veteran`, `World Baseball Classic`.
- Type changes clear `series`, because non-player types currently often return `series: Default`; a stale `series=Live` can make Equipment/Stadium/etc. look empty.
- `App.tsx` also drops stale series params when the newly fetched result set does not contain that series.
- Sort and series values should be normalized before passing them to MUI `Select` controls to avoid out-of-range value errors from missing/invalid params or casing differences such as `world baseball classic` vs `World Baseball Classic`.

Sorting
- Sort options in `src/marketUtils.ts`:
  - Buy now (`best_sell_price`)
  - Sell now (`best_buy_price`)
  - Buy now vs avg (`buy_now_vs_all_time_average_diff`)
  - Profit/hr (`profit_per_hour`)
  - Spread (`spread_number`)
  - Spread % (`spread_percentage`)
  - Profit (`profit`)
  - Profit % (`profit_percentage`)
  - Overall (`rank`)
- The effective default list sort is `Overall` / `rank` when no valid `sort` param exists.
- `normalizeSort` returns a safe sort key for invalid/missing URL params.
- Sort direction is URL-backed by `sortDirection`.
- Default sort direction:
  - `best_sell_price` defaults ascending.
  - all other sorts default descending.
- The sort dropdown has a minimum width and should not collapse before a user picks a value.
- `Buy now vs avg` relies on cached all-time averages from `market_card_averages`.
- `Profit/hr` is a liquidity-aware flip sort. It should use cached stored-order liquidity inputs plus the current live listing prices, not raw full-history scans in the browser.

Price, spread, profit, and quick-sell logic
- `getListingPrices` in `src/marketUtils.ts` returns:
  - `buyNow`: `best_sell_price`
  - `sellNow`: `best_buy_price`, unless missing/0 and a quick-sell fallback exists.
- Quick-sell fallback exists for player cards and supported non-player item types/rarities.
- Do not apply quick-sell fallback to cards where `item.is_sellable === false`; those catalog-only/non-sellable cards should show missing market prices rather than fake sell-now values.
- `isUsingQuickSellFallback` drives the `QuickSellBadge`.
- Spread is `buyNow - sellNow`, floored at 0.
- Sale tax is 10%.
- Profit is spread minus 10% of buy-now.
- Profit percentage is profit divided by sell-now.
- `Profit/hr` should only use actual market buy-now/sell-now prices. Do not use quick-sell fallback for this metric; a card with no live buy side is not an active flip target.
- Cached liquidity inputs come from `market_card_liquidity`:
  - `buyMatchCount`
  - `sellMatchCount`
  - `buyFillRatePerHour`
  - `sellFillRatePerHour`
  - `windowHours`
  - `confidence`
- The current formula is an adjusted expected flip rate:
  - compute current profit from live market buy/sell prices
  - compute expected cycle time as `(1 / buyFillRatePerHour) + (1 / sellFillRatePerHour) + handlingHours`
  - estimate pipeline throughput as the smaller of observed market throughput (`min(buyFillRatePerHour, sellFillRatePerHour)`) and the human slot cap (`activeFlipSlots / expectedCycleTime`)
  - use `activeFlipSlots = 7` as the default human-realistic number of simultaneous flips
  - assume a default human-realistic working bankroll of `75,000` stubs, and reduce active slots to `floor(stubBudget / sellNow)` when the acquisition cost makes the requested number of copies unrealistic
  - when `Profit/hr` is selected, show visible controls for stub budget and flip slots below the primary sort/filter controls and above the `Filters` button; default the inputs to `75,000` and `7`, and store non-default values in URL params
  - multiply `profit * realisticFlipsPerHour` by cached confidence
- Liquidity window selection:
  - prefer 24h if both buy and sell match counts are at least 3
  - otherwise fall back to 7d
- Liquidity price matching uses a band of `max(50 stubs, 2% of the reference price)` around:
  - current `best_buy_price` for buy-fill matches
  - current `best_sell_price` for sell-fill matches
- Sort/list metric rendering should keep using the shared helpers so quick-sell behavior is consistent everywhere.

SearchPanel UX
- The sidebar should feel like a compact market workstation, not a landing page.
- Search is debounced.
- Type and rarity are visible primary controls.
- Sort dropdown plus explicit asc/desc icon button are visible primary controls.
- The minimum spread field is only visible when sort is `Spread %`.
- Profit/hr tuning fields (`Stub budget`, `Flip slots`) are only visible when sort is `Profit/hr`, positioned above the `Filters` button, and should update the list sort plus row metric without refetching listings.
- Star controls are local user preferences stored on the user's device, not market data caches. List rows and the selected detail header have star icon buttons. The visible `Starred only` toggle sits next to the `Filters` button and filters the current fetched list by starred UUIDs.
- Post-query filters live behind a `Filters` button in a right-side drawer:
  - series
  - min/max buy now
  - min/max sell now
- The `Filters` button shows the active post-query filter count in a small MUI badge.
- `Clear all` is on the main SearchPanel row, not hidden inside the drawer. It clears pre-query filters (`query`, `itemType`, `rarity`) and post-query filters (`series`, min/max buy/sell, minimum spread). It does not change sort settings directly.
- The virtualized list uses a local scroll container, fixed row height, and overscan.
- The list does not auto-scroll to the selected item.
- Search/filter/sort changes reset the list scroll position to the top.
- Clicking a list row updates `uuid` in the URL and selects that item.

Market detail workflow
- `MarketDetail` reads the selected `uuid` from URL params.
- The detail header includes a star icon button for the selected listing, using the same local starred UUID store as the list.
- A local Refresh button increments component state so the selected detail page and order history reload without retriggering the whole list fetch in `App.tsx`.
- Detail loading sequence:
  - fetch live listing detail via `fetchListingByUuid`
  - fetch cached all-time average via `/api/cards/:uuid/average`
  - fetch cached liquidity via `/api/cards/:uuid/liquidity` for the detail `Profit/hr` card
  - fetch recent stored completed orders using `RECENT_ORDER_LOOKBACK_DAYS` (7 days)
  - fetch long-term stored completed orders using `ALL_ORDER_LOOKBACK_DAYS` (3650 days)
- Recent/all-order fetches fall back to the live API sample if local history is unavailable or empty.
- Summary cards currently show:
  - Buy now
  - Sell now
  - Profit
  - Profit/hr
  - All time average
  - 7-day trend
- The detail `Profit/hr` card must use the same shared calculation and URL params (`profitHrActiveFlipSlots`, `profitHrStubBudget`) as list sorting/rendering.
- `All time average` must come from the cached average API/table, not from recomputing all orders in the frontend.
- The all-time average card also shows a signed `current +/-N` badge representing current buy-now vs cached all-time average.
- `7-day trend` is derived from price history over the latest 7-day window.
- Detail view also shows daily price history, completed orders by hour, all completed orders table, and all completed orders chart.

Cached average source of truth
- The source of truth for player/card average price is the backend SQLite table `market_card_averages`.
- All average-price UI and sort logic should use the cached average endpoints:
  - `/api/cards/averages`
  - `/api/cards/:uuid/average`
- Do not reintroduce frontend recomputation of all-time average from the long all-orders dataset for list/detail cards.
- Backend robust averages use `calculateRobustAverage` in `src/orderStats.ts`.
- The robust average removes outlier trade prices with an IQR-based calculation using a widened `3.0 * IQR` fence.
- The cached average table exists because scanning millions of `stored_completed_orders` rows during page load is too slow.
- Startup warms `market_card_averages` once if the table is empty and stored orders already exist. The first server start after introducing or clearing the table may pause while warming.
- Collection and on-demand detail refresh update each affected card's cached average after new orders are inserted, or if an average row does not exist yet.

Cached liquidity source of truth
- The source of truth for list-level liquidity inputs is the backend SQLite table `market_card_liquidity`.
- This cache exists so `Profit/hr` sorting can stay fast without running one raw-order aggregation per card in the browser.
- Frontend list sorting should fetch cached liquidity rows from:
  - `/api/cards/liquidity`
- Backend can also expose:
  - `/api/cards/:uuid/liquidity`
- Collection and on-demand detail refresh should refresh cached liquidity for the affected UUID so the stored price bands stay aligned with current market prices.
- Startup should warm `market_card_liquidity` once if the table is empty and local order history already exists.

Backend behavior
- `src/server/marketServer.ts` loads `.env` if present and reads config through `readConfig`.
- Default backend config:
  - API base: `https://mlb26.theshow.com/apis`
  - host: `127.0.0.1`
  - port: `4000`
  - DB path: `market.sqlite`
  - collector interval: 1 hour
  - collector concurrency: 4
  - request delay: 150ms
  - static dir: `dist`
- SQLite tables:
  - `market_cards`: latest known card/listing metadata and raw JSON.
  - `stored_completed_orders`: normalized completed orders keyed by unique source hash.
  - `market_card_averages`: cached robust all-time averages.
  - `market_card_liquidity`: cached recent buy/sell match counts, fill rates, and confidence for `Profit/hr`.
  - `collector_runs`: run status and stats.
- Important indexes:
  - `idx_stored_completed_orders_uuid_time` on `(uuid, order_time)`.
- API routes:
  - `GET /api/health`: ok, collection state, row counts, last run.
  - `GET /api/show/listings.json`: proxy to MLB The Show listings API.
  - `GET /api/show/items.json`: proxy to MLB The Show item catalog API.
  - `GET /api/show/listing.json`: proxy detail API and persist completed orders from the response.
  - `GET /api/cards/:uuid/orders?days=N`: stored completed orders for one card/item.
  - `GET /api/cards/liquidity`: all cached liquidity rows.
  - `GET /api/cards/:uuid/liquidity`: one cached liquidity row.
  - `GET /api/cards/averages`: all cached average rows.
  - `GET /api/cards/:uuid/average`: one cached average row.
  - `POST /api/collect`: trigger collection.
- The backend serves the built frontend from `dist/` when available; otherwise API-only mode is active.
- CORS defaults to `*` unless `CORS_ORIGINS` is configured.
- The collector fetches all market listings across all item types, persists cards, fetches each listing detail, stores completed orders, and updates cached averages.
- `collectionInFlight` prevents overlapping collection work.

Data and API notes
- MLB item types used by the app: `mlb_card`, `stadium`, `equipment`, `sponsorship`, `unlockable`.
- `/api/show/listings.json` proxies market listings and omits non-sellable catalog-only cards.
- `/api/show/items.json` proxies the broader item catalog. Use it when a player-card series/checklist view needs to show every card, including non-sellable cards with no current market price.
- Non-player types can have different metadata fields than player cards. Use optional access patterns and shared helpers.
- Equipment, Sponsorships, Stadiums, and Unlockables commonly have `series: Default`; this matters when thinking about series filters.
- The frontend API client builds paths from `VITE_BACKEND_API_BASE`, `VITE_SHOW_API_BASE`, and `VITE_HISTORY_API_BASE` when present; otherwise it uses same-origin `/api/show` and `/api`.
- `VITE_HISTORY_API_ENABLED=false` disables local history fetches and returns empty history/average data.
- Frontend API helpers should not cache market data in memory or local storage unless a future product decision explicitly reintroduces caching with freshness controls.
- Local storage is acceptable for user preferences such as starred listing UUIDs. Do not store market price/listing/order payloads there under the current no-frontend-market-cache rule.

Deployment and server lifecycle
- The intended always-on Linux setup is a systemd service installed by `scripts/install-systemd-service.sh`.
- This Windows development machine must not run the long-running backend service. The always-on service role is reserved for the Linux server only.
- On Windows, use local dev commands only when needed for short-lived verification work. Do not leave the backend/dev server running as a persistent service on this computer.
- Service name defaults to `mlb-show-market-checker`.
- `start.sh` runs the backend server with `tsx src/server/marketServer.ts`.
- Deploy-on-push uses `.github/workflows/deploy-home-server.yml` on a self-hosted Linux runner.
- Deploy script: `scripts/deploy-from-git.sh`.
- Deploy script behavior:
  - refuses dirty working trees
  - requires Node 25+
  - checks the live clone is on the expected branch
  - fetches/fast-forwards from `origin/main`
  - runs `npm ci`
  - runs `npm run build`
  - restarts the systemd service unless `SKIP_SERVICE_RESTART=1`
- A successful deploy should end with a service restart. If pages act stale after deploy, check GitHub Actions logs, `sudo systemctl status mlb-show-market-checker`, and `sudo journalctl -u mlb-show-market-checker -n 100 --no-pager`.

Design and UX principles for this app
- This is an operational market-analysis tool. Prefer dense but readable controls, restrained styling, and predictable workflows.
- Do not build landing-page or marketing-style UI for the core app.
- Put controls where users need them. Example: `Clear all` belongs near the visible filter controls, not hidden inside the drawer.
- Keep text inside controls stable and unsquished. Give controls minimum widths where needed.
- Prefer icons for compact toggles such as sort direction, with accessible labels/tooltips.
- Avoid auto-scrolling surprises. The list should reset to top when query/filter/sort criteria change, but selecting an item should not force-scroll the list to that item.
- When adding filters, decide whether they are fetch inputs or post-query/local transforms. Fetch inputs affect API calls; post-query filters should reuse the current fetched list.
- If a filter can become stale after another control changes, clear or normalize it rather than showing an empty list that looks broken.

Verification expectations
- For frontend/TypeScript changes, run `npm run typecheck -- --pretty false`.
- For app behavior changes, run `npm run build` unless the change is documentation-only.
- Keep the known Vite chunk warning in mind; it does not by itself mean the build failed.
- When diagnosing list bugs, test the exact URL/query-param combination and determine whether the issue is:
  - API fetch scope
  - local search matching
  - post-query filter state
  - sort normalization
  - MUI Select value mismatch
  - cached average availability
